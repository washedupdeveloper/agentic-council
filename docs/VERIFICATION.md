# Verification: the next milestone

Every claim this repository makes must be checked by something that can fail, or be
deleted. This file is the checklist; a row without a passing command is open work.

## Definition of done

| # | what is verified | how | acceptance |
|---|---|---|---|
| 1 | every function | a generated map from function to the test(s) that call it | no function has zero callers *and* zero tests; each exception is listed below with a reason |
| 2 | every docstring that asserts a fact | a claim in `claims.toml`, a test, or rewritten as prose without a fact | no docstring states a number, a guarantee or a failure mode that nothing checks |
| 3 | every comment | same rule as 2 | a comment that explains *why* is kept; one that asserts *what* is checked or removed |
| 4 | every document in `docs/` | `tests/test_docs_index.py` (linkage) plus a claim per factual statement | the index test passes and every "N of M" or "always/never" sentence is backed |
| 5 | every decision record | each acceptance-table row is a command that runs in the gate | every row executes green in CI |
| 6 | the Nix package | `nix build .#packages.<system>.default`, then run the binary | the binary reports its version and `--help` works from the store path |
| 7 | the flake as an input | a fixture flake in this repository that consumes `self` | it builds, runs and `nix flake check`s green |
| 8 | CI/CD | the gate workflow plus the same fixture check | a push to `v2` runs both without a self-hosted runner |

## Method for 1–3

The map is generated, not maintained: a script walks the AST of every module, records each
function's qualified name, then records every call site and every test that reaches it
through pytest collection. A function with no caller and no test is reported. A docstring
or comment that contains a number, "always", "never", "only", "cannot" or "fails" is
reported with its line, and each is resolved one of three ways: linked to an existing
claim, given a new claim, or reworded so it asserts nothing checkable.

The output is a table in this file, regenerated by the same script, so the checklist cannot
drift from the tree.

## Discoveries so far

- `nix flake show` lists `checks` for four systems but prints no `packages` section, while
  `packages.x86_64-linux.default` builds. The surface a consumer relies on is therefore not
  discoverable by the command people use to discover it. Either the output is genuinely
  absent or the listing is wrong; both are defects worth fixing before claiming usability.
- A `path:` input locks by content hash, not by revision, so a consumer's lock file records
  no `rev` (verified: `nodes.council.locked.rev` is null). A `github:` input would carry a
  revision; the fixture check must cover the path a stranger actually uses.
- `bwrap` on a hosted runner is present-or-absent and separately *usable-or-not*; only the
  second condition matters, and the tests originally checked the first.
