# M28 — Rules, proof strength, and publication

Four changes, all taken from reviewing `deepseek-ai/deepseek-harness` (0.2.2-rc.3):
its review skill, its review of its own code, and its storage discipline. Each
one answers a question this tool had been answering by omission.

## 1. Rules: judge the diff against the repository's documents

**Problem.** dsh's `dsh-code-review` skill states the rule plainly: *"Read the
requirements before judging the diff… Judging a diff against memory of the rules
is how a violation passes review."* council had `--context-url` (caller-supplied
pages) and nothing that tied a repository's own documents to the paths they
govern. Every review was judged against the model's memory of what a repository
probably wants.

**Decision.** `council.toml` may map a path glob to the document that governs it:

```toml
[[rules]]
glob = "packages/goal/**"
doc = "docs/subsystems/goal.md"
```

A rule whose glob matches a changed path contributes its document to the prompt
once, under a heading that frames the text as **context from the repository, not
instructions**, capped at 20,000 bytes and marked when cut. A rule that matches
nothing is not recorded. A rule whose document cannot be read is a start failure:
silently continuing would send the reviewer back to judging from memory, which is
the failure the feature exists to prevent. `verdict.json` records what governed
the change (`rules[].glob/doc/paths/truncated`).

**Rejected.** Injecting the documents without a cap (a repository could make the
prompt unbounded); skipping an unreadable document with a warning (the reviewer
would not know it is judging from memory); reading documents from outside the
checkout (a rule is repository-controlled input).

**Known limit.** A rule document is repository-controlled text in a model prompt.
The heading frames it as data and the cap bounds its size, but a repository that
wants to steer its own review can — which is also true of the diff itself.

## 2. Proof strength: a quotation is not a behaviour

**Problem.** In the dsh review, eight findings proved claims about control flow
(an unbounded loop, a missing clamp, a scanning cost) by quoting the defective
line. Under the proof rules those are `PROVEN`; under the truth they are
`PROVEN that the line exists`. The default still let them block.

**Decision.** Every finding records `proof_strength`: `executed` when the proof
that held ran something (`command`, `repro`), `static` when it only quoted
(`present`, `absent`, `json`, `diff`). The verdict's reason names blocking
findings that rest on quotation alone. `--require-executed-proofs` excludes them
from blocking entirely; the run then passes (or fails on the executed ones) and
the reason still names what was quoted.

**Rejected.** Making `executed` mandatory (breaks the large class of real defects
that are one wrong line — a hard-coded secret, a missing guard — and no caller
asked for that); hiding the distinction (it is the single most useful thing a
reader can know about a proven finding).

## 3. An atomic, versioned verdict

**Problem.** `verdict.json` was written in place. A crash mid-write leaves a
partially written document that a CI consumer reads as invalid JSON and reports
as a tool crash; a consumer that predates a field cannot tell which format it is
looking at.

**Decision.** The document is staged in the same directory, flushed, `fsync`ed
and renamed into place: a reader sees the old file or the whole new one. It
states `format: 1`, and `docs/VERSIONING.md` says a consumer must refuse a format
it does not know rather than guess.

**Rejected.** Writing to a temp directory and copying (not atomic across
filesystems); a schema URL (a network dependency in a verdict).

**Known limit.** There is a format number and no published JSON Schema. A
consumer can detect a version, not validate a document.

## 4. A bounded report

**Problem.** The dsh audit produced a 3.1 MB `verdict.json` whose bulk was
21,629 `scope_ignored` records against five findings. A report nobody can read
the end of is not a report, and the size is unbounded by anything the caller
controls.

**Decision.** `scope_ignored` names at most 200 paths and `scope_ignored_omitted`
counts the rest. The count is kept because the alternative — silently truncating
— would hide that the review did not look at 21,429 files.
