# M32 — Expose V2 through ACP and MCP without changing the core

The request was to make the existing V2 review gate available to someone using
Zed's Agent Panel, VS Code, OpenCode or another MCP/ACP host. It was not a
request to redesign the review engine.

## Decision

Add two optional adapters around the public CLI:

- `council-mcp` — a local stdio MCP server exposing `council_plan`,
  `council_review` and `council_doctor`.
- `council-acp` — a local stdio ACP external agent exposing `/plan`, `/review`,
  `/verdict` and `/help`.

Both invoke the installed `council` command with `--json`, parse the existing
verdict document and preserve the exit code. The server retains evidence under
its own state root with `--keep`; it never writes `.council` into the reviewed
repository.

The V2 core is untouched: no changes to `src/council`, the prompt, proof kinds,
verdict schema, exit codes, or the Hermes reviewer path. The additions are
optional packages, entrypoints, tests, Nix outputs and documentation.

`pyproject.toml` carries extras `mcp`, `acp` and `server`. Nix exposes separate
closures `council-mcp`, `council-acp` and `council-server`; the plain `council`
package keeps no protocol SDK.

## Why two adapters

ACP and MCP are different products, not two transports for the same API:

- An ACP server is an agent in an editor's Agent Panel. It owns a session and a
  model.
- An MCP server provides tools to an existing agent. The host owns the
  conversation; council is called as a tool.

They share one subprocess boundary and one review contract.

## Rejected

- **Refactor a `ReviewService` out of the CLI.** Not needed to expose the tool;
  it would change the core and create a second way to construct a review.
- **Use the host editor's model as the reviewer.** Neither protocol gives a
  server the host's model inference; this needs a separate host-model contract
  and would change evidence provenance.
- **A separate `council-server` distribution initially.** It would add a second
  version and release process. Optional extras plus Nix variants preserve one
  version; split later if dependency pressure appears.
- **Remote MCP/HTTP and authentication.** Local stdio is the useful first
  transport; remote serving is a separate deployment decision.
- **Code editing, PR comments or automatic merge.** Council remains a gate.

| 32.1 | the MCP server lists exactly its three tools | `pytest tests/test_mcp_server.py::test_mcp_lists_the_three_tools -q` |
| 32.2 | MCP plan equals the CLI plan | `pytest tests/test_mcp_server.py::test_mcp_plan_is_the_cli_plan -q` |
| 32.3 | MCP review runs the real CLI gate and retains evidence | `pytest tests/test_mcp_server.py::test_mcp_review_runs_the_gate_and_exposes_evidence -q` |

| 32.5 | the ACP agent returns the gate verdict | `pytest tests/test_acp_agent.py::test_acp_review_returns_the_gate_verdict -q` |
| 32.6 | the subprocess boundary returns the CLI result | `pytest tests/test_server_cli.py -q` |

The protocol tests use the official MCP and ACP SDK clients, a real council CLI
and a deterministic fake reviewer. The reviewer output uses one `present`
proof, so the verdict is settled by the core proof executor rather than by test
prose.

## Known limits

- stdio only; no remote MCP transport or authentication;
- the reviewer is server-configured, not the host model;
- ACP exposes deterministic review commands, not general chat;
- `council pr` and baseline commands are not server tools yet;
- A Zed UI session is a manual acceptance step; the SDK client is the automated
  protocol proof.

## Verification

The regular V2 gate remains authoritative: pytest, mypy, pyright, ruff F/E9,
`council-verify`, mutation checks and `nix flake check`. The new tests are part
of the same suite; they are not a separate, weaker gate.
