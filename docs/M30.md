# M30 — Every assertion carries its source

The rule this milestone enforces: **nothing in this repository is assumed.** Not
by the skill an agent follows, not by the verdict a person acts on. Every claim
either resolves to a file that can be opened, or it is not a claim the tool is
allowed to make.

Two places were still asserting without a trail.

## 1. The verdict asserted findings it could not point at

`verdict.json` said `F-01, proven, security, a.py:2, "It is wrong."` and stopped.
The sample files existed, but nothing connected the finding to the answer that
produced it: a reader had to search every `sample-N.json` for a matching line and
hope. Worse, `merge` was called with one flat list of every finding from every
unit and every sample, so `MergedFinding.samples` was always `(1,)` — the field
existed and meant nothing.

**Decision.** The run builds one list per sample, in run order, and names the file
each was written to. `merge` carries those labels onto the merged finding, and
`verdict.json` writes them as `findings[].evidence`:

```json
{"id": "F-01", "state": "proven", "location": "a.py:2",
 "evidence": ["sample-1.json", "sample-2.json"]}
```

The chain is now complete and checkable:

    finding → findings[].evidence → sample-N.json → the raw answer
            → prompt.md → digest (prompt + profile config + diff sha256)

A sliced run names `units/<unit-id>/sample-N.json`, so a windowed finding points
at the window that produced it.

**Rejected.** A run-level `samples[]` list only (it says a sample ran, not which
finding it asserted); storing the raw answer inside `verdict.json` (duplicates
the evidence and doubles the file); a `sample_index` integer (an index is not a
path, and a path is what a reader can open).

**Known limit.** A finding merged from several samples names all of them, so a
reader still has to read more than one file to see the disagreement. That is the
honest form: the disagreement is the evidence.

## 2. The skill asserted a CLI it did not declare

`skills/council/SKILL.md` is what an agent reads before running the tool. It
named commands, flags and artefacts in prose, and a test checked only that the
verbs it mentioned existed. Everything else — which flags exist, which artefacts
a run produces, whether the body and the tool still agree — was assumed.

**Decision.** The skill declares its surface in frontmatter, and a test binds the
declaration to the CLI in both directions:

```yaml
commands: [review, ci, pr, baseline, init, doctor]
flags: [--plan, --include, --exclude, --samples, --report, --json, --sarif,
        --no-ephemeral, --keep, --require-executed-proofs, --base]
artefacts: [verdict.json, sample-N.json]
```

- every declared command answers `--help` with exit 0;
- every subcommand the parser offers is declared — a new verb cannot ship
  undocumented in the skill;
- every declared flag exists in the parser;
- every `--flag` the body names is declared — prose cannot invent a flag;
- every declared artefact is explained in the body.

**Rejected.** Generating the skill from `--help` (a skill is judgement about how
to use a tool, not a flag dump); a YAML dependency (the frontmatter is five
`key: [a, b]` lines; a hand parser is smaller than the dependency and the repo
ships zero runtime dependencies).

**Known limit.** The binding covers commands, flags and artefacts. It cannot
check that the *advice* is good — that a `static` proof is weaker than an
executed one is a judgement, and it is stated as one.
